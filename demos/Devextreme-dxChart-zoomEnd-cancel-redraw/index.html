dxChart: a visualRange rejected by the zoom limit leaves the chart half-rendered

T1335913. A live line chart with aggregation follows the newest data: every second the new dataSource and the new argumentAxis.visualRange go in as one option update. After "Zoom In" narrows the window to 30 s, hovering the line throws Cannot read properties of null (reading 'styles') on every mouse move, the tooltip never appears and the argument axis stops following the data.

What happens. A visual range that arrives together with something that needs a full render (new data, a new tickInterval) is applied in one pass: the points are recreated, the chart is drawn, and only then the zoomEnd handlers run. Without minVisualRangeLength the axis rejects any window shorter than whole range / plot width (24 h over ~1180 px is about 73 s), so the 30 s zoom is canceled and the previous range is restored. The restore goes through the same visual range handler, which skips its render because the "full render" flag is still set - although that render has already happened. The axis ends up with the old range while the DOM shows the rejected one; with aggregation the restore also recreates the points, which disposes the ones that were just drawn, and the tracker's hit-test cache keeps pointing at them. Every next update repeats the cancel, so it never recovers. The same inconsistency exists without aggregation and when a zoomEnd handler sets e.cancel = true, only without the crash; and a polar chart never raised zoomEnd for a batched valueAxis.visualRange at all.

The fix. The full render clears its own flag once it is done, so a visual range change requested after it (the restore, or an API call from a zoomEnd handler) renders itself; raising zoomEnd after the full render moved from dxChart to the shared AdvancedChart, so polar charts get it too. The rejection itself is by design: to zoom below the limit, set minVisualRangeLength (the "workaround" switch below does exactly that).

+ remove(code) {

  _change_FULL_RENDER() {

chart_components/advanced_chart.ts (moved here from chart.ts)
+ _change_FULL_RENDER(): void {
+   super._change_FULL_RENDER();
+   if (this._changes.has(VISUAL_RANGE)) {
+     this._raiseZoomEndHandlers();
+   }
+ }
  _change_VISUAL_RANGE(): void {
    this._recreateSizeDependentObjects(false);
    if (!this._changes.has('FULL_RENDER')) {   // now false after the full render of the same pass
      this._doRender({ ... });
      this._raiseZoomEndHandlers();
    }
  }

Frames

Both frames run the sample from the ticket on 26.2.0 built from the same tree, the only difference between the two bundles is the change above. Each frame zooms in and hovers the line by itself 1.5 s after it loads; data keeps arriving every second, exactly as in the sample. "Hover the line" moves the pointer over the middle of the drawn line the way a mouse would - a real hover does the same. The log at the bottom of each frame records every update: the axis range against the requested one, whether the rendered ticks lie inside that range, and how many drawn points are already disposed.
