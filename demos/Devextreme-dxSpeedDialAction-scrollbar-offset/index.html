dxSpeedDialAction: the 16px right offset is swallowed by the scrollbar

The FAB is placed against the window. calculatePosition in __internal/common/core/animation/m_position.ts took the window's width as innerWidth whenever innerWidth > outerWidth. innerWidth includes the classic scrollbar, documentElement.clientWidth does not, so the whole 16px offset is spent on the scrollbar and the button ends up flush against it. Chrome reports outerWidth === 0 until the first frame is painted, which is exactly when widgets are created on document ready, so the comparison fires by mistake. Any later window resize repopulates outerWidth and the overlay re-renders its geometry, which is why resizing "fixes" the button.

The change

 
- h.atSize = of[0].innerWidth > of[0].outerWidth ? of[0].innerWidth : getWidth(of);
- v.atSize = of[0].innerHeight > of[0].outerHeight || IS_SAFARI ? of[0].innerHeight : getHeight(of);
+ const isOuterSizeKnown = of[0].outerWidth > 0 && of[0].outerHeight > 0;
+
+ h.atSize = isOuterSizeKnown && of[0].innerWidth > of[0].outerWidth
+   ? of[0].innerWidth
+   : getWidth(of);
+ v.atSize = (isOuterSizeKnown && of[0].innerHeight > of[0].outerHeight) || IS_SAFARI
+   ? of[0].innerHeight
+   : getHeight(of);

outerWidth = 0 shows up when the page is the first document of a freshly created browser window; on a warm reload the value is already there. Both states were reproduced in headless and headful Chrome. Because a page can only watch its own pre-first-frame moment once, the frames below set the state explicitly: window.outerWidth is [Replaceable], so assigning to it is what the QUnit suite has always done.
